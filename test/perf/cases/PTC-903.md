# PTC-903 — MOCK-903 per-stream RSS at N concurrent SSE streams

**Requirement (GAP-005 corrected form).** MOCK-903 (903.1/903.2): hold **≥20 000
concurrent open SSE streams per process** for 5 min, zero drops, with **RSS ≤ 1.5
GiB** (ADR-012's envelope, stated as a target to be confirmed by measurement).

**CRITICAL ARCHITECTURAL PRECONDITION — established by code inspection.**
In this Phase-1 build the mcpmock **engine never selects the SSE shape**
(`internal/transport/httpx/jsonsink.go:86-87`, `doc.go:35`: *"Phase 1 emits only
buffered JSON; the SSE framing and content semantics are Phase 2"*). The only MCP
verb, POST `/mcp`, returns a **buffered JSON response and closes the connection**;
GET/DELETE return **405** (MOCK-207, confirmed by smoke test). **There is
therefore no request that opens a long-lived live SSE stream through the running
server on this build.** MOCK-903 cannot be exercised end-to-end via the public
HTTP surface in Phase 1. This is itself a finding, not a defect to work around.

**What CAN be measured honestly.** The exported Phase-2 seam
`httpx.Server.Stream(ctx, *SSESink, keepAlive)` + `httpx.NewSSESink(w, onClose)`
+ the shared timer wheel is the exact code that will carry a Phase-2 stream.
TASK-019 already benchmarked it against `httptest.ResponseRecorder`s and got
≈2.9 KiB/stream — but that is **Go-heap only** and *explicitly excludes* the
largest contributors (net/http read goroutine, bufio buffers, kernel socket
buffers). This test drives the same seam over **real accepted TCP sockets** and
measures **process RSS**, which includes those contributors, at the largest N the
host allows.

**Target environment.** `localhost`, Apple M1 Max. macOS default per-process fd
limit is low; `ulimit -n` raised for the harness shell (reported). Loopback
means both stream ends live in the same box, so kernel socket-buffer memory for
BOTH endpoints is charged to this host — an *over*-count relative to a real
client on another machine, which is stated.

**Tool + why.** A purpose-built Go harness (`test/perf/cmd/ssebench`), NOT k6:
k6's SSE support cannot exercise a seam that no HTTP verb reaches, and the honest
memory number needs RSS of the server *process* at N live sockets. The harness
starts the httpx server, opens N real TCP client connections, has the server
drive `Stream` on each over the accepted conn, holds them open, and samples RSS.

**Load profile.** Step N ∈ {1000, 2000, 5000, 10000, 20000} live streams (as far
as the fd/host limit allows). At each N: open all, hold ≥30 s with the 15 s
keep-alive firing, `runtime.GC()`, sample RSS and goroutine count, record
per-stream RSS delta over the baseline (server with 0 streams).

**Autostop / host-limit conditions.** Stop climbing N at the first of: fd
exhaustion (`too many open files`), dropped/failed stream establishment, or RSS
approaching host memory pressure. Report which fired.

**Monitored metrics.** Process RSS (`ps -o rss`), `runtime.NumGoroutine`,
Go `HeapAlloc` (for the TASK-019 comparison), open-fd count, streams
successfully established vs attempted.

**Pass criteria (verdict).** Report the **RSS-based per-stream cost** and the
**max N reached**. Judge whether ADR-012's ~1.5 GiB / 20 000-stream envelope
survives, and state whether ADR-012's ~25 KiB or TASK-019's 2.9 KiB is closer to
the live-socket reality and why. If 20 000 live streams cannot be reached on this
host, the verdict is INDETERMINATE-ON-THIS-HOST for the *count* but the
*per-stream RSS* extrapolation to 20 000 is still reported with its method.

**Runs.** ≥3 per N; report spread. **Expected duration.** ~20 min.
