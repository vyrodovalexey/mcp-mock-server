# PTC-902 — MOCK-902 throughput with FULL journaling

**Requirement.** MOCK-902 (902.1): sustain **≥5000 rps** for 60 s with
`journal.bodies: full` and a bounded ring, **p99 < 50 ms**, error rate < 0.1%.
(902.2) RSS stabilises after the ring fills.

**Target environment.** Same as PTC-901 — `localhost`, Apple M1 Max, labelled
*measured on this host* vs *target*.

**Tool + why.** `k6` v1.7.1, open model `constant-arrival-rate`. Same rationale
as PTC-901.

**Load model.** Open model. Offered rate fixed at the target.

**Load profile.**
- Warm-up: 30 s at 5000 rps — discarded.
- Steady state: 60 s at 5000 rps with full journaling (100 000-record ring,
  `CaptureFull`, default `drop-oldest` overflow).
- Ramp: 5k → 10k → 20k → 40k rps, 20 s/step, to locate the journal-path knee and
  compare the saturation point against the journaling-off run (the single
  variable changed between PTC-901 and PTC-902 is the journal mode).

**Data characteristics.** Identical request to PTC-901 so the *only* changed
variable is journaling. Full body capture means each request writes a record;
the ring is bounded, so 902.2 (RSS stabilises after fill) is observable within
the 60 s window (100 000 records fill in 20 s at 5000 rps).

**Autostop / abort conditions (MANDATORY).** `http_req_failed rate < 0.01`
(abortOnFail) and `http_req_duration p(99) < 500ms` (abort ceiling; verdict
ceiling is 50 ms in analysis).

**Monitored metrics.** As PTC-901, plus RSS watched specifically for
post-ring-fill stabilisation (902.2).

**Pass criteria (verdict).** PASS iff achieved ≥ 5000 rps sustained 60 s AND
p99 < 50 ms AND error < 0.1% AND RSS stabilises AND generator unsaturated.

**Runs.** ≥3; report spread. **Expected duration.** ~15 min.
